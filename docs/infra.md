# NCP 운영 구성과 검증

## 현재 구성 · 2026-10-13

| 역할 | 배치 | 운영 목적 |
|---|---|---|
| App | KR-1·KR-2 각 최소 1, 최대 2 | 웹 화면·API, 총 기본 2·최대 4대 |
| Worker | KR-1 고정 1대, KR-2 고정 1대 검증 중 | MySQL 작업 큐와 공유 CLOVA 호출 예산 |
| Cloud DB for MySQL | 두 존의 주·대기 서버, Private | 업무 데이터·작업 큐, HA |
| LB | 공개 Application LB | App 8080으로 분산, /actuator/health 검사 |
| NAT | 각 존 Public Subnet | Private App·Worker의 외부 API 통신 |
| Bastion | Public, 허용 관리 IPv4 /32 | 공개키 SSH 관리 |
| Object Storage | 비공개 버킷 | 녹음 저장 기반. 전사는 실제 통합 상태에 따라 시연 |
| Cloud Insight | 서버·DB·LB 지표, 관리 경보 | 장애·부하 확인과 운영 기록 |

App·Worker는 Ubuntu 24.04, Java 21이다. App과 Worker는 역할을 분리하며 Worker에 HTTP LB를 연결하지 않는다. 각 Worker ASG의 SVR 검사는 VM을 교체하고 systemd가 프로그램을 재시작한다. 프로그램 hang 감지나 전체 존 장애 시험은 별도 과제다.

현재 자원 ID·IP·배포 해시·원출력·state·캡처·비용 보고서는 인프라 담당자의 **로컬 관리표 한 곳**에 보관한다. 이 문서에는 공유할 구성과 검증 범위만 기록한다. 이전 Rocky 및 초기 Ubuntu 목록은 로컬 이력으로 보존했으며 현재 자원 목록으로 사용하지 않는다.

## App 수의 결정

기준은 p95 500ms 미만, 오류율 1% 미만이다. 기본 2대는 300 VU 정상 p95 약 32ms, 한 대를 중지하고 LB가 제외한 후 남은 한 대 p95 약 373ms·오류율 0%로 확인했다. 정상·장애 각각 1회이며 장애 직후 무중단 보장은 아니다.

600 VU 비교는 NCP의 동일 부하 발생기, 같은 jar·2vCPU/8GiB App·DB·회의록 466건·조회 패턴을 사용했다. 각 조건 3회, 워밍업 60초·측정 120초다.

| 600 VU 조건 | p95 중앙값 | 통과 |
|---|---|---|
| 2대 정상 | 833ms | 0/3 |
| 3대 정상 | 411ms | 3/3 |
| 3대 중 1대 중지 후 | 862ms | 1/3 |
| 4대 중 1대 중지 후 | 308ms | 3/3 |

정상 처리에 필요한 최소 3대에 한 대 장애 여유를 더해 상한 4대를 유지한다. 공유 계정 3개의 조회 부하이며 실제 독립 사용자 600명이 아니다. 600 피크에 장애 여유가 필요하면 미리 4대를 확보한다. CPU 정책의 확장 지연과 용량 상한은 서로 다른 값이다.

## Worker 안정성 변경과 결정 기준

공유 예산의 잠금 오류를 실제 MySQL에서 재현했다. 행 초기화와 예산 예약을 별도 짧은 트랜잭션으로 분리하고, 잠금 실패는 새 트랜잭션에서 최대 3회 재시도한다. HTTP와 대기는 트랜잭션 밖에 둔다.

독립 심박은 15초마다 90초 임대를 갱신한다. ID·상태·소유권 버전·만료 시각을 확인해 만료된 임대를 되살리지 않는다. 최종 저장도 소유권을 다시 검증한다. Worker 두 대는 동일한 CLOVA 계정·quota scope를 공유하므로 API 한도가 두 배가 되지 않는다.

검증 순서: 새 PR CI → 단일 Worker canary → 임시 KR-2 Worker → 50건씩 각 3회 → 두 존에서 프로세스·VM 중지와 인계. 새 작업 시작 30초·중단 작업 재시작 120초 조건은 호출 예산과 생존 Worker 슬롯에 여유가 있는 통제 시험에 적용한다. 분석 전체 완료시간의 보장은 아니다.

최종 두 대 유지는 150건씩 성공·원문 근거 일치·내부 잠금 실패 없음과 장애 인계 통과 후 결정한다. 외부 AI 호출은 장애 재시도 때 중복될 수 있지만 최종 업무 결과는 하나여야 한다. 처리량 개선과 가용성 이득을 구분한다.

## 접근 규칙과 라우팅

| 대상 | 인바운드 허용 | 목적 |
|---|---|---|
| Bastion | 관리 IPv4 /32의 TCP 22 | 공개키 SSH |
| App | LB 서브넷 TCP 8080, Bastion ACG TCP 22 | 서비스·관리 |
| Worker | Bastion ACG TCP 22 | 관리, HTTP 포트 없음 |
| DB | App·Worker ACG TCP 3306 및 상품 HA 규칙 | 클라이언트·DB HA |

Private App·Worker는 존별 NAT 경로를 사용하고 DB에는 인터넷 기본 경로를 추가하지 않는다. NACL은 기본 NACL을 유지하며 구체적인 접근 제어는 ACG로 수행한다. NACL은 서브넷, ACG는 서버에 적용한다. [NCP 공식 비교](https://guide.ncloud-docs.com/docs/vpc-nacl-vpc).

DB 인바운드 검증에서는 Bastion의 출구만 DB 두 주소 TCP 3306으로 잠시 허용했다. 같은 DB가 Bastion 연결은 거부하고 Worker 연결은 허용했으며 DB 규칙은 변경하지 않았다. 임시 출구 규칙은 제거하고 원래 규칙과 일치함을 확인했다. 공개 인터넷에서 사설 IP에 연결할 수 없다는 사실로 이 시험을 대신하지 않았다.

## 보안과 모니터링

- 무토큰·위조 토큰 401, 다른 조직 조회 403을 확인했다.
- 존재하는 합성 Storage 객체의 인증 GET 200·익명 GET 403을 확인하고 시험 객체를 삭제했다.
- 등록된 키의 추적 파일·최근 24시간 로그 노출을 검사했다. 환경 파일은 root 0600, SSH는 공개키만 허용한다.
- Bastion의 전체 IP SSH 허용 규칙을 발견해 제거하고 허용 관리 접속을 확인했다.
- 관리 경보는 본인 EMAIL만 선택했다. CPU 70% 3분, 메모리 80% 5분, DB 연결 상한 70% 5분이다.
- 기존 App 확장 CPU 80% 3분·축소 30% 10분 정책과 관리 경보를 분리한다.
- 독립 테스트 경보의 발생·발송 처리·복구를 확인했다. **실제 메일 수신은 본인 확인 대기**다. ASG 교체 통보 설정은 콘솔 로그인 후 별도로 확인한다.
- 경보 대상은 ASG로 묶었다. 서버 교체 후 실제 대상·SSH 별칭·관리표를 점검한다. DB 정적 대상 변경 시 수동 갱신한다.

현재 HTTP, DB TLS·저장 암호화 미적용인 합성 데이터 데모다. 접근 제어를 암호화라고 표현하지 않으며 침투 시험이나 침해 부재를 보장하지 않는다. 실제 회의 데이터 운영 전 HTTPS·DB 전송/저장 보호·이미지 밖 비밀 주입과 키 회전을 보완한다.

## 변경·비용·복원

실행 담당자 한 명이 원래 운영 state를 사용한다. 별도 state로 apply하지 않는다. .env·tfvars·state·plan·개인키는 Git 제외 및 권한 0600이다. 원격 state·잠금은 아직 미구현이다.

현재 Worker 코드 변경은 PR #13의 infra/ubuntu-runtime 기반이다. main의 팀원 기능과 마이그레이션 통합은 별도 작업이며 자동 병합하지 않는다. 오래된 checkout 코드로 apply하면 검증용 Worker B가 삭제될 수 있으므로 최종 결정 전 별도 apply하지 않는다.

225만원은 예산이다. 서버뿐 아니라 중지 디스크·이미지·스냅샷·LB·NAT·공인 IP·DB·Storage·CLOVA를 점검한다. 계정 전체 월 사용료 API는 프로젝트별 비용이나 즉시 확정된 결제 금액과 구분한다. 예산 75%에서 비필수 시험, 90%에서 신규 청구 자원을 중단한다.

이번에 추가한 임시 규칙·객체·서버만 정리한다. 기존 롤백 자원과 발표 후 운영 자원은 자동 삭제하지 않는다. 삭제 예정일·실제 청구 정보는 로컬 관리표에 기록한다.
