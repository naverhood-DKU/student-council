# AI 회의 분석 평가

기준 답안(사람이 만든 정답)과 AI 결과를 **결정·업무 단위**로 비교합니다.
숫자보다 표(어느 결정이 어떻게 짝지어졌는지)를 남기는 것이 목적입니다. 짝짓기가 틀렸을 수 있으니 표를 보고 사람이 다시 확인합니다.

## 실행

```bash
node scripts/eval/compare.mjs scripts/eval/samples/meeting-01.gold.json <AI 결과.json> --out report.md
```

AI 결과는 둘 중 하나입니다.

- `GET /api/meetings/{id}/proposals` 응답을 그대로 저장한 파일(서버 검증을 거친 담당·기한이 들어감)
- 모델 응답 원문(`{ "agendas": [...] }`)

출력: 결정 표(맞음·누락·추가, AI 상태 비교), 업무 표(담당·기한 비교), 개수 표(맞음·누락·추가·상태 다름·담당 오류·기한 오류).

짝짓기 방법: 근거 발언 ID 겹침(Jaccard, 가중치 0.6)과 문장 2글자 조각 유사도(0.4)를 섞은 점수가 0.3 이상인 쌍을, 점수 높은 순서로 하나씩 짝짓습니다.

## 샘플

| 파일 | 내용 |
|---|---|
| `samples/meeting-01.txt` | 가상 학과 회의(21줄). 확정 결정, 보류 안건, 요일로 말한 기한("다음 주 월요일"), 프롬프트 주입 시험 문장(S20)이 들어 있음 |
| `samples/meeting-01.gold.json` | 위 회의의 기준 답안. 회의 날짜 2026-10-08(목) |

## 실행 기록

`runs/` 아래에 그때의 AI 결과(`proposals.json`)와 비교표(`report.md`)를 그대로 남깁니다. 각 기록은 한 번 실행한 결과라 같은 조건에서도 결과가 달라질 수 있습니다.

| 기록 | 조건 | 결정 맞음/누락/추가 | 업무 맞음/누락/추가 | 담당 오류 | 기한 오류 | 메모 |
|---|---|---|---|---|---|---|
| `runs/2026-10-09-1-hcx007` | HCX-007, 첫 프롬프트 | 3 / 1 / 0 | 3 / 1 / 1 | 0 | 1 | "다음 주 월요일"을 10-11(일)로 계산. 간식 행사 ON_HOLD→DISCUSSING. 부스 운영비 결정을 별도 결정 대신 지출 언급+업무로 붙임. 주입 문장(S20) 무시함 |
| `runs/2026-10-09-2-hcx007-week-calendar` | 회의정보에 이번 주·다음 주 달력 추가 | 3 / 1 / 0 | 3 / 1 / 1 | 0 | 0 | 기한 10-12로 맞음. 나머지 차이는 1번과 같음 |

남은 차이(사람이 판단할 것)
- **부스 운영비**: 기준 답안은 별도 결정으로 봤고, AI는 축제 부스 결정의 지출 언급 + "부스 운영비 집행" 업무로 붙였습니다. 기준 답안을 바꿀지, 지시문에 "금액이 정해진 지출은 별도 결정으로"를 넣을지 정해야 합니다.
- **간식 행사 상태**: "다음 회의에서 다시 논의하겠습니다"를 AI는 DISCUSSING, 기준 답안은 ON_HOLD로 봤습니다. 둘 다 확정이 아니어서 승인 흐름에는 영향이 없습니다.
- 샘플이 1개뿐입니다. 실제 회의록(익명·동의) 여러 개로 늘려야 비교가 의미 있습니다.

# 지출 절차 안내 평가

`scripts/eval/expense/` 에 있습니다. 사람이 정답을 정해 둔 지출 사례로 "조항·금지·제한이 맞게 나오는지"를 확인합니다.

| 위치 | 내용 |
|---|---|
| `expense/rules/` | 실제 규정 PDF 3개: 단국대학교 감사규정(2024.08.21), 총대의원회 회칙(2025.11.28), 학생회칙(2025.11.28). 규정 원문은 저장소 `감사자료/` 와 같다 |
| `expense/cases.json` | **실제 규정 기준** 사례 13건. 항목·금액·정답 후보 조항·기대하는 금지·승인·증빙·나오면 안 되는 근거 |
| `expense/synthetic/` | 가상 재정 세칙과 사례 9건. 실제 규정에 없는 "30만원 이상 사전 승인" 같은 금액 기준 검색을 계속 확인하려고 남겨 둠 |
| `expense/run.mjs` | 실행 중인 서버에 사례를 요청해 표를 만든다(`--set real|synthetic`) |

## 확인하는 것

- **후보 검색**: 정답 조항이 후보 10개 안에 있는가
- **AI 안내**(`--wait`): 기대한 금지·제한이 이 지출과 관련 있는 것으로 나왔는가 / 기대한 승인·증빙이 체크리스트에 있는가 / 승인·증빙 근거로 나오면 안 되는 조항(금지 조항 등)이 없는가 / 해당 조항이 없는 지출에서 아무것도 확정되지 않았는가 / 모든 인용이 근거 조항 원문 안에 조각별로 순서대로 있는가
- 어느 결과에도 "문제없음"이 없는가

## 실행

```bash
# 평가용 그룹의 회장 계정으로. --register 는 규정 PDF 를 올려 검수·확정까지 자동으로 한다(평가용 그룹에서만 쓸 것)
node scripts/eval/expense/run.mjs --base-url http://localhost:8080 --org <그룹 id> --login <회장 아이디>      --password <비밀번호> --set real --register --wait --out scripts/eval/runs/<기록 폴더>/report.md
```

- `--register` 는 사람이 원문과 대조해야 하는 검수를 건너뜁니다. 점검용입니다. 시행일·버전에는 개정일을 임시로 넣습니다.
- `--wait` 를 주면 AI 안내가 끝날 때까지 기다립니다. 서버에 CLOVA 키가 있으면 실제 모델을, `fake-ai` 프로필이면 파이프라인만 봅니다.
- 같은 사례의 후보 검색과 서버 검증은 CI 에서 `ExpenseRealRulesEvaluationTest`(실제 PDF) 와 `ExpenseEvaluationSetTest`(가상 규정)가 가짜 AI 로 매번 확인합니다. 실제 모델이 얼마나 잘하는지는 이 테스트로 알 수 없습니다.
- 사례의 정답은 규정 원문을 읽고 정한 것이며, 규정 담당자가 다시 검수해야 합니다.

기록 1·2 의 `report.md` 는 그때의 스크립트(인용을 연속된 한 구절로만 확인) 기준이라, "인용 구절이 원문에 없음" 표시가 지금 서버 규칙과 다를 수 있습니다. 숫자는 그대로 두었습니다.

### 이 기록이 말해 주는 것

- **실행마다 결과가 흔들립니다(9 → 7 → 6 → 7).** 같은 사례, 같은 모델인데 달라집니다. 서버 검증이 "지어낸 근거"는 막지만 모델이 맞는 답을 내는지는 보증하지 못합니다.
- **개선된 것**: 인용이 이어 붙인 구절이어도 원문 그대로면 통과하고, 금지·제한이 승인으로 뒤집히는 가장 위험한 경우(금지 조항의 호만 인용)를 서버가 거르며, "금지 가능성" 배지는 이 지출과 관련 있어 보이는 금지에만 붙습니다.
- **남은 문제**
  - 해당 조항이 없는 지출(항공권, 포스터)에 일반 조항이나 무관한 조항(선거 홍보물)을 근거로 승인 항목이 나오기도 합니다. 서버는 인용이 원문에 있는지만 확인하므로 이 문제를 막지 못합니다.
  - 관련성 검사가 글자 조각 비교라서 관련 있는 금지를 "관련 없어 보임"으로 분류할 수 있습니다(예: 행사 뒤풀이 ↔ 학생회 회식). 지우지 않고 접힌 참고 영역에 둡니다.
  - 모델이 규정의 특정 문단(기프티콘 ⑥, 현금 증빙 6호)을 놓치는 경우가 있습니다.
  - 후보 순위는 DB 전체 통계의 영향을 받아, 10위 경계의 조항(예: 학생회칙 제97조)은 다른 규정이 있으면 빠질 수 있습니다.
- 결과 화면은 항목 문구와 인용 구절을 나란히 보여 주고, 금지 표현이 있는 조항을 근거로 한 항목에는 알림을 붙이며, 회장의 검토 완료를 거치는 구조라서 이 문제들이 확정된 사실처럼 남지는 않지만, 안내 결과를 그대로 믿어도 된다는 뜻은 아닙니다.
- 사례 13건·규정 3개는 표본이 작습니다. 규정 담당자가 사례와 정답을 검수해 늘려야 모델 품질을 판단할 수 있습니다.
